# Выбор и настройка мониторинга в системе

## Мотивация

Яндекс Метрика описывает поведение посетителей магазина, но партнёрские вызовы MES API, обработка сообщений, состояние заказов и работа операторов в неё не попадают. Сейчас о потерянных и просроченных заказах команда узнаёт от клиентов. Мониторинг должен показать, сколько заказов приняли, сколько дошло до каждого состояния, сколько времени занял переход и где растёт очередь. Это позволит звонить клиенту с конкретным ответом, исправлять сбой до потери контракта и оценивать, помогает ли изменение системы. Первую пользу можно получить без перестройки всех приложений: собрать показатели существующих API, RabbitMQ и БД, затем добавить бизнес-метрики.

## Выбор подхода к мониторингу

Для Shop API, CRM API, MES API и внешнего партнёрского входа применяю RED: частота запросов, доля ошибок и длительность. Для EC2, PostgreSQL, RabbitMQ и worker расчёта цены применяю USE: загрузка, насыщение и ошибки. Четыре золотых сигнала покрываются сочетанием этих подходов; отдельный набор дублировал бы показатели. Отдельно считаем принятые заказы, переходы между статусами и просрочки. Для незавершённых заказов измеряем время в текущем статусе. Из HTTP 200 невозможно вывести, создан ли заказ в CRM.

Один набор дашбордов показывает B2C и B2B рядом, но с раздельными значениями `channel`. Срезы по статусам и каналам имеют ограниченное число значений. `order_id`, `customer_id`, `user_id`, `trace_id` и произвольный URL в ярлыки Prometheus не попадают: каждый новый идентификатор создал бы отдельный временной ряд. Их место в журнале событий и трассах. Имя маршрута задаётся шаблоном вроде `/orders/{id}`.

## Метрики

Из списка в задании выбраны метрики, которые помогут найти причины задержек и потери заказов. К ним добавлены показатели обработки заказов и работы дашборда MES. Для всех рядов общие ярлыки `env` и `service`; для инфраструктуры также `instance`. Частоты считаются из счётчиков через `rate`, ошибки сервера по классу 5xx, длительность из гистограмм с p50, p95 и p99. Ярлыки ниже перечислены сверх общих.

В HTTP-метриках `channel` принимает B2C, B2B или internal для действий сотрудников без клиентского входа. В бизнес-метриках канал берётся из записи принятого заказа и остаётся B2C или B2B, даже когда статус изменяет оператор. Приложение назначает ярлыки по своему маршруту и данным БД, а не доверяет произвольному значению из запроса.

Брокер опрашивается через штатный Prometheus plugin RabbitMQ, ресурсы VM через node_exporter, Spring Boot через Micrometer, C# через OpenTelemetry Metrics. Метрики управляемых БД берутся из облачного мониторинга; длительность запросов и ожидание свободного соединения дополнительно измеряются в приложении. Время доставки считается обработчиком как разница между началом обработки и `occurred_at` события. Возраст необработанного события получается из сверки outbox и inbox, а не из чтения головы рабочей очереди: такой диагностический потребитель изменил бы доставку. Это время включает ожидание до публикации и в обработке, поэтому на панели оно не называется возрастом ready-сообщения.

Prometheus собирает метрики Spring Boot и инфраструктуры через защищённые HTTP-адреса экспортёров. Для C# API и отдельного worker выбираю пакет `OpenTelemetry.Exporter.OpenTelemetryProtocol`: метрики отправляются напрямую в Prometheus по OTLP/HTTP с `OtlpExportProtocol.HttpProtobuf`, через `AddOtlpExporter` в настройке `MeterProvider`. Полный адрес экспортёра оканчивается на `/api/v1/otlp/v1/metrics`; Prometheus запускается с `--web.enable-otlp-receiver`. Метрики отправляются каждые 15 секунд. Счётчики и гистограммы передают накопленные значения с начала работы процесса. Доступ разрешён только из сети приложений с TLS и аутентификацией. Трассы отправляются на отдельный адрес Collector из Task3, поэтому его остановка не прерывает доставку метрик. Для отдельного worker выбран OTLP: ему не нужен собственный HTTP-сервер для выдачи метрик. Экспортёр на базе HttpListener в рабочем окружении не используется.

Версии SDK и Prometheus фиксируются после проверки совместимости. В release проверяются итоговые имена метрик, границы интервалов гистограмм и перенос атрибутов окружения, сервиса и экземпляра в ярлыки `env`, `service`, `instance`. Для OTLP-процессов scrape-метрика `up` не возникает. Каждый процесс экспортирует `app_heartbeat_timestamp_seconds` с текущим временем при сборе; по списку ожидаемых экземпляров проверяются отсутствие ряда и возраст значения более 60 секунд. Так обнаруживается и остановленный worker, и разрыв доставки метрик. Недоступность самого Prometheus проверяется внешней пробой. Время от коммита нового доступного заказа до показа измеряется в release на управляемых E2E-сценариях; браузерная телеметрия prod даёт распределение времени загрузки и отрисовки, но сама по себе не знает о ещё не показанном заказе.

HTTP-счётчик имеет имя `http_requests_total` и ярлыки `route`, `method`, `status_class`, `channel` сверх общих. Таймер `http_request_duration_seconds` использует те же ярлыки, кроме `status_class`; приложения приводят экспорт к этой схеме. Доля ошибок сервера равна частоте ответов 5xx за 5 минут, делённой на частоту всех ответов за тот же интервал, с одинаковыми фильтрами сервиса и маршрута. При нулевом числе запросов доля не определяется и не подменяется успешностью 100%. p95 вычисляется через `histogram_quantile` по сумме bucket-рядов, а не усреднением p95 нескольких инстансов. Границы HTTP-гистограммы включают 0.1, 0.5, 1, 2 и 5 секунд; расчёт цены имеет отдельную гистограмму с границами 60, 120, 180, 600, 1800 и 2100 секунд. CPU показывает использование; ожидание пула и рост очереди показывают насыщение. Один высокий CPU без задержки ещё не повод масштабировать сервис.

Число ответов 2xx вычисляется из общего счётчика по `status_class`. Эта схема не различает 200, 201 и 202; отдельный подсчёт HTTP 200 для выбранных задач не нужен. Ответ 202 подтверждает приём запроса, а результат обработки проверяют бизнес-метрики. RPS на каждого пользователя и число одновременных сессий не решают текущую проблему и либо создают слишком много временных рядов, либо требуют отдельно определять, что считается сессией; при расследовании злоупотреблений используем журнал API и отдельные лимиты по ключу партнёра. Объём переданных килобайт полезен только при проверке дорогой загрузки 3D-файлов, поэтому добавляется позже на маршрут загрузки, без пользовательских ярлыков. Нулевой поток заказов при работающем API показывается на дашборде как факт; сам по себе он не означает инцидент.

### Как вычисляются показатели заказов

Для B2C принятым считается заказ после фиксации SUBMITTED в Shop DB. Для B2B точка приёма должна быть долговечной записью входящего запроса с `order_id` в MES DB до ответа об успешном приёме. Если сейчас MES отвечает раньше записи, это дефект, который исправляется до запуска SLI. `accepted_at` берётся из этой записи в UTC. Источник текущего статуса и `status_entered_at` определяется владельцем перехода, приведённым в Task1; история фиксируется в транзакционном журнале. Каждый заказ связывается между системами по `order_id`, а не разницей двух счётчиков за одинаковые минуты. Счётчики переходов служат для динамики потока, не для поиска пропавшего заказа.

| Показатель | Правило расчёта и окно | Источник и обновление |
|---|---|---|
| Сейчас принят, но не найден в CRM | Текущее число уникальных заказов, у которых прошло больше 40 минут от `accepted_at`, а CRM-записи до сих пор нет. Это очередь проблем для разбора, без ограничения последними сутками. | Сверка по `order_id` раз в минуту. Для B2C правило включается после подтверждения маршрута из магазина в CRM. Список ID остаётся в защищённой таблице, Prometheus получает агрегат по каналу. |
| SLI создания в CRM за 40 минут | Знаменатель: заказы с `accepted_at` в интервале от `now - 24 часа - 40 минут` до `now - 40 минут`. Числитель успешности: из них заказы с `crm_created_at <= accepted_at + 40 минут`. Поздно восстановленный заказ остаётся нарушением в этой когорте, хотя из текущей очереди проблем уже исчез. | Журнал приёма, первое время создания CRM и история сверки. Порог включает расчёт до 30 минут и запас на очередь; уточняется после замеров. |
| Текущее ожидание и SLI обязательного перехода | Для алерта считаются открытые шаги с истёкшим `step_deadline_at`. Для SLI за сутки знаменатель включает шаги, чей deadline попал в последние 24 часа; числитель включает завершённые не позднее deadline. Успешный поздний переход не стирает историческое нарушение. | Watchdog из Task3 подтверждает переходы по журналам владельцев и сохраняет их времена, deadline и факт нарушения. Экспортируется агрегат по `channel`, `step`, `threshold_class`. |
| SLI доставки в обещанный срок | Знаменатель: принятые заказы с `promised_at` в последних 90 днях до текущего момента. Числитель: из них заказы с подтверждённым получением `delivery_confirmed_at <= promised_at`. Неполученные заказы входят в знаменатель. Отмена в кейсе не описана, поэтому исключений пока нет. | `promised_at` фиксируется при приёме: 21 календарный день от `accepted_at` для B2C, если продажи подтверждают именно срок получения; для B2B берётся срок договора. Иначе отдельно измеряется обещанный срок производства или отправки. Ручное закрытие учитывается только с проверяемым основанием доставки. Расчёт ежедневно из CRM и журнала доставки. |
| Возраст открытого заказа и текущего статуса | Возраст заказа равен `now - accepted_at`, возраст статуса равен `now - status_entered_at`. На дашборд идут максимум и фиксированные интервалы возраста, без ID. | Авторитетные БД и Watchdog, обновление раз в минуту. Подробный список остаётся в интерфейсе поддержки. |

При пустом знаменателе SLI показывается как отсутствие измерений. Отдельная метрика считает заказы без `promised_at`, времени приёма или сопоставленного ID. Недоступный источник не даёт новых подтверждённых значений: панель показывает давность сверки и неизвестное состояние. Если полнота данных не подтверждена, SLI помечается неполным. Исключённые записи не должны улучшать статистику. Бизнес-показатели за 90 дней пересчитываются по журналу БД; хранение Prometheus за 30 дней не ограничивает эту когорту.

Если маршрут B2C или источник факта доставки отличается от описанного, владелец процесса утверждает точную запись и алгоритм перед включением алерта. Это не меняет принцип: метрика строится по множеству конкретных заказов, а не по корреляции общего трафика.

## План действий

1. Согласовать с продажами, производством и поддержкой точку приёма заказа, обещанный срок, источник подтверждения доставки и смысл каждого статуса. Проверить маршрут B2C до CRM. Зафиксировать определения SLI и окна измерения. Сначала собрать данные за неделю, затем согласовать целевые показатели качества, SLO.
2. Развернуть Prometheus для временных рядов, Grafana для дашбордов и Alertmanager для маршрутизации уведомлений в prod; хранить метрики 30 дней локально, затем решить по объёму, нужна ли долговременная удалённая запись. Метрики dev и release хранить отдельно от prod, разграничить доступ и правила оповещений.
3. Подключить экспортёр RabbitMQ, системные и PostgreSQL-метрики управляемого облака. Проверить, какие показатели Managed Service доступны через API облака; отсутствующие получить экспортёром с учётной записью только для чтения. Для каждого опрашиваемого экспортёра настроить проверку `up`, для C# проверить поступление heartbeat по OTLP.
4. Инструментировать Spring Boot и C# API общими HTTP-счётчиками и гистограммами; добавить отдельные таймеры расчёта цены, SQL дашборда и обработчиков событий. Счётчики увеличивать после коммита, но точное число заказов рассчитывать по уникальным записям БД: процесс может упасть между коммитом и обновлением счётчика. Запустить минутную сверку по `order_id` и защищённую таблицу результатов, из которой экспортируются агрегаты.
5. Построить дашборды для дежурного и бизнеса: путь заказа по каналам, очередь и DLQ, p95 API и SQL, ресурсы, соблюдение срока. Добавить ссылки из алерта к дашборду и инструкции разбора.
6. Настроить алерты и проверить их на тестовом остановленном потребителе, искусственном 5xx и задержке расчёта. Назначить владельцев реакции и еженедельно разбирать ложные срабатывания. Вводить алерты поэтапно, чтобы одна команда могла их обслуживать.

## Насыщение и реакция

Пороги ниже предлагаются для первого запуска. После двух недель измерений и нагрузочной пробы их уточняют: важно понять, при какой нагрузке система начинает заметно замедляться. Для большинства сигналов задана длительность превышения, чтобы короткий всплеск не вызывал лишний вызов дежурного. Новое сообщение в DLQ и блокировка публикаций брокером требуют реакции сразу.

Использование CPU и памяти показывает занятость ресурса. Рост очереди, ожидание соединения и блокировки показывают, что свободной мощности уже не хватает. Бизнес-просрочки и отсутствие свежей диагностики также приведены в таблице как отдельные сигналы; их нельзя лечить автоматическим добавлением инстансов.


Пороги соединений 70% и 85% оставляют запас до отказа в подключении. Рост времени ожидания показывает, что пул уже мешает обработке запросов. Пороги CPU 75% и 90% используются вместе с задержкой или очередью: сама по себе высокая загрузка может быть нормальной. Для обычных событий 5 минут дают время заметить отставание, а 15 минут требуют срочного разбора, поскольку сообщения о смене статуса не должны ждать столько же, сколько сам расчёт цены. Дисковые пороги 20% и 10% дают время освободить или добавить место до остановки записи. Эти значения нужно проверить с учётом скорости роста данных.

| Сигнал | Предупреждение и критический порог | Реакция |
|---|---|---|
| Старейшее необработанное событие перехода | Более 5 минут, затем более 15 минут при обычном потоке. Ожидание задачи расчёта и сам расчёт учитываются отдельно. | Тикет и сообщение дежурному; при критическом пороге звонок, проверка outbox, потребителя и DLQ, увеличение worker только при подтверждённом вычислительном упоре. |
| DLQ и необработанные события | Любое новое сообщение в DLQ вызывает тикет; более 10 неразобранных или рост 10 минут подряд вызывает критический алерт. | Остановить бесконтрольные повторы, определить причину, исправить и переиграть с идемпотентностью. |
| Соединения с БД и пулы приложений | Более 70% лимита 10 минут; критично более 85% 5 минут вместе с ростом ожидания свободного соединения. Отдельно проверяются общий лимит подключений PostgreSQL и ёмкость каждого клиентского пула. | Проверить долгие транзакции и пулы клиентов, ограничить параллелизм; увеличение БД после профиля запросов. |
| CPU MES worker и API | Свыше 75% 10 минут, затем 90% 5 минут при росте p95 или очереди. | Уменьшить конкуренцию тяжёлых расчётов и добавить worker. API масштабировать после проверки, что узкое место не БД. |
| p95 дашборда MES | Цель p95 до 2 секунд после базового замера; критично более 5 секунд 10 минут при наличии запросов именно к дашборду. | Проверить SQL, блокировки, кеш и ресурсы. |
| Принятый заказ без обязательного шага | Хотя бы один заказ без CRM-записи после 40 минут или без следующего перехода после порога из Task3. Повторить проверку на двух минутных циклах, чтобы исключить временный сбой чтения. | Создать карточку конкретного заказа для поддержки и дежурного, проверить источник истины, очередь и DLQ. В Prometheus передавать только число нарушений. |
| Срочный заказ без назначения | Заказ остаётся в срочной очереди более 30 рабочих минут после включения в неё | Начальник смены назначает подходящего свободного оператора либо фиксирует препятствие и эскалирует руководителю производства. Возраст и число таких заказов контролируются отдельно от p95 успешных назначений. |
| Оформление заказа | Резкое падение доли успешных фиксаций SUBMITTED или B2B-приёма среди запросов именно на оформление, если за 10 минут было не менее 20 таких попыток; порог отклонения определить по базовой линии. | Проверить 4xx/5xx, валидацию и фронтенд. При меньшем числе попыток полагаться на синтетический заказ и сверку уже принятых заказов. Просмотры каталога и запросы статуса в знаменатель не входят. |
| Ресурсы брокера и дисков | Любой активный memory/disk alarm RabbitMQ; свободное место менее 20% как предупреждение, менее 10% как критический сигнал | Проверить blocked connections, остановить необязательные потоки, освободить безопасно удаляемые данные и увеличить ёмкость. Сами заказы из очередей не удалять. |
| Redis и координация списка MES | Память более 80% `maxmemory` 10 минут вместе с ростом evictions и miss; ожидание ревизий увеличивает p95 записи статуса более чем на 10% от варианта без кеша | Проверить размер и число ключей, TTL и пользу кеша. При замедлении записи отключить кеш флагом и убрать обновление ревизий только после отключения кеша во всех экземплярах API. |
| Сверка и доставка диагностики | Нет успешной сверки 3 минуты; `up=0` 2 минуты; растёт число отброшенных записей или буфер заполнен более чем на 80% 5 минут | Алерт дежурному DevOps. При отказе сверки состояние заказов показывается как неизвестное; отсутствие метрик не закрывает открытые инциденты. |

Метрики Spring Boot и VM собираются каждые 15 секунд. C# отправляет метрики по OTLP с тем же интервалом, а сверка заказов выполняется раз в минуту. `/metrics`, Prometheus и Alertmanager доступны только из служебной сети; Grafana обращается к источникам со своего сервера под отдельными служебными учётными записями. Поддержка видит бизнес-панели в своей организации, инженеры технические. Dev и release отделены от prod сетевыми доступами и источниками данных: ярлык `env` сам по себе не ограничивает права. Для каждого алерта задаются `severity`, владелец, время ожидания и ссылка на инструкцию. Независимая внешняя проверка контролирует доступность критического API и heartbeat мониторинга, чтобы отказ Prometheus не оставил команду без уведомления.

Автоматическое добавление инстансов разрешается только для stateless API и отделённого worker с верхним лимитом и контролем очереди. Для БД и брокера автоматический скейлинг без анализа может усугубить перегрузку. При нарушении бизнес-срока по конкретным заказам система формирует рабочий список для поддержки и продаж; идентификаторы остаются вне метрик.

Alertmanager направляет уведомления ответственным, объединяет повторяющиеся сигналы и позволяет временно отключать оповещения на время согласованных работ.
